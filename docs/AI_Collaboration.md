# 与AI编码助手协作

AI可以协助理解代码、设计接口、实现功能、定位失败和检查差异。开发成员负责确定需求、确认工程范围、理解实现并验证提交。按一个可测试功能推进，比一次要求生成整个系统更容易联调和评审。

## 1. 准备上下文

1. 克隆仓库，在AI编码工具或编辑器中打开AD-CausalRisk根目录。
2. 阅读README并运行一次Python示例，确认本机地址和请求格式。
3. 让AI读取AGENTS.md、需求、联调约定、目标接口及对应模块README。AGENTS.md是项目规则；工具未自动读取时，在提示中明确要求它阅读。
4. 告知系统和版本、本人负责模块、当前分支、本次需求、现有代码与实际错误。
5. 先检查计划和涉及文件，再开始实现；修改共同契约时先与团队确认。

不要把数据库密码、访问令牌或个人资料作为上下文。提供去除敏感内容的配置示例、请求/响应和必要错误堆栈。

## 2. 通用任务单

```text
项目：AD-CausalRisk
负责模块：[backend/frontend/python_service]
当前分支：[本人功能分支]
需求编号：[例如FR-DATA-01]
本次目标：[具体行为，限定一个可验收功能]
环境：[系统、语言版本、构建命令、数据库/API地址]
已有实现：[相关文件或接口]
验收场景：[正常、参数错误、权限、空数据、失败]
允许修改：[目录/文件]

先阅读AGENTS.md及相关需求、契约，检查现有实现。
说明步骤与涉及文件，然后实现并运行相关测试。
共同字段和版本保持一致；需要改变时先说明影响并由团队确认。
结束时给出改动摘要、实际测试和未验证项，不自动推送或合并。
```

## 3. 后端首次任务模板

```text
我负责backend。请阅读AGENTS.md、backend/README.md、课程需求、
Design_Guide和Java目标OpenAPI。

本次只建立Spring Boot工程、数据库迁移与档案创建/分页查询。
使用Java 21；构建方式和Spring Boot版本先检查现有文件，
没有配置时提出一致的方案，并固定依赖。
按Controller/Service/Repository分层，使用DTO和统一Envelope。
保留subjectCode到数字主键的映射、唯一约束、分页上限和输入校验。
配置用环境变量，添加.env.example时仅写占位值。

覆盖正常创建、重复编号、非法参数、分页和数据库迁移测试。
在backend/README.md记录启动/测试命令。
登录与权限若尚未实现，明确该依赖并保留测试计划，
不能宣称已通过完整角色验收。
只改backend及必要模块说明，不修改Python评分或共同契约。
```

接下来的任务分别完成认证/权限、导入、质控、任务与AgentClient、随访/报告/审计。不要让AI在一次任务中同时建立所有模块并遗漏失败场景。

## 4. 前端首次任务模板

```text
我负责frontend。请阅读AGENTS.md、frontend/README.md、课程需求、
Design_Guide和Java目标OpenAPI。

本次只完成前端工程、路由、集中API客户端、登录页和档案列表。
先检查已有技术栈；新工程建议Vue 3，依赖与锁文件一起提交。
接口类型按契约定义；Java未完成时使用可明确关闭的Mock。
覆盖加载、空数据、失败和无权限状态。
表单支持键盘，桌面与手机布局可读；错误不能被静默吞掉。

添加客户端/组件测试，记录开发、构建、测试与Mock启停命令。
只改frontend，不改Java/Python来绕过尚未完成的接口。
给出实际运行结果、页面截图方法及未完成项，不自动提交推送。
```

后续分开完成导入、质量、任务、图谱/解释、患者摘要、随访和报告。已有Mock不是最终联调证明；每个功能都需要切换到实际Java接口验证。

## 5. AgentClient联调任务模板

```text
请阅读Python OpenAPI、Java目标OpenAPI及Integration_Contract。
实现backend中的AgentClient和任务结果映射，不改变Python协议。

调用POST /api/agent/v1/runs，重试沿用同一runId。
验证contractVersion、modelVersion、workflowVersion、runId和结果结构。
COMPLETED保存结果；BLOCKED保留null分数和原因。
超时、服务不可用、409版本/请求冲突进入明确失败状态并记录traceId。
任务和返回结果持久化，重启Java后仍可查询。
Python没有实时阶段推送，完成后展示实际轨迹与耗时。

用Mock HTTP测试超时、5xx、409、响应缺字段和BLOCKED，
再执行一次实际Python服务调用。列明哪些检查实际执行。
```

## 6. 修复失败时提供什么

粘贴执行命令、运行目录、版本、相关文件、预期结果、实际错误及最近改动。堆栈保留定位所需部分，不带凭据。可以使用：

```text
本次只修复下面失败，不重构无关模块。
命令与目录：[...]
预期结果：[...]
实际错误：[...]
相关文件与最近改动：[...]

先复现或说明无法复现的原因，再定位、修复并重跑相关检查。
不要删除失败测试、放宽校验或用假成功结果消除错误。
说明修复依据、实际验证及剩余问题。
```

## 7. 检查AI生成的代码

每次实现后检查：

- 文件是否仅在本次范围内，是否误改他人模块或锁文件。
- 接口路径、字段、枚举和版本是否与契约一致。
- Controller/Service/Repository或页面/组件/API客户端是否各司其职。
- 失败、空数据、无权限、超时和重复提交是否有明确处理。
- BLOCKED是否保持null分数，患者接口是否由后端过滤。
- 依赖是否必要并记录版本，配置是否含明文凭据。
- 测试是否真正执行，是否包含功能行为和失败场景。

让AI检查差异的提示：

```text
请只审查本分支相对origin/main的差异，结合需求与契约检查。
找出可定位的问题及影响，引用文件和位置，给出修复建议。
重点看权限、状态转换、幂等、版本、数据持久化、错误处理和测试。
这一步不自动改代码，不把未运行的测试当成已验证。
```

## 8. 验证与提交

先运行模块的真实命令，再运行受影响的共同检查。Python公共检查：

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests -v
```

Linux/macOS使用`.venv/bin/python`。Java和前端的构建、测试命令由各成员维护到模块README。没有测试环境时明确未验证，不用截图或AI口头判断替代。

```bash
git status
git diff
git diff --check
# 确认改动和测试后，选择本次相关文件
git add backend
git commit -m "Add subject management"
git push -u origin backend/subject-management
```

提交前让AI整理PR说明可以使用：

```text
根据当前差异整理PR标题和说明：需求编号、实现行为、接口影响、
实际测试与截图、未完成项。不要加入聊天背景或假设测试结果。
只生成说明，不代我推送、创建或合并PR。
```

## 9. 新会话如何接续

让AI先读取最新分支和git diff。记录模块、需求、已改文件、已执行命令、实际失败、当前决定和下一步；不要让后续AI凭上一段聊天猜工程状态。长任务可在本人分支提交一份简短任务说明，合并前整理为面向团队的模块文档。

```text
请继续当前分支，先检查AGENTS.md、需求、代码和git diff。
已经完成：[文件与行为]
实际验证：[命令与结果]
尚未完成：[具体项]
下一步只做：[范围]
请核对这些信息与代码是否一致，再继续，不重复创建已有工程。
```

团队评审后合并PR，下一项功能从最新main创建分支。AI的建议不能替代本人理解、运行验证和团队评审。
