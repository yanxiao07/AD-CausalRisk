## 2. 系统导读

这一章是给第一次接触项目的同学看的。先理解系统要解决什么问题，再看后面的接口和代码结构，会更容易知道自己负责的功能在整条流程中的位置。

### 2.1 为什么要做这个系统

阿尔茨海默病相关研究通常会同时记录很多种信息：基本档案、历次访视、认知量表、APOE 遗传信息和 MRI 影像等。这些资料往往分散在不同表格里，记录时间也不一样。研究人员如果只看其中一种数据，很难形成完整判断；如果直接把所有数据塞给模型，又可能因为缺失、重复或时间不一致而得到不可靠的结果。

因此，本项目要做一个“研究资料整理 + 风险关注提醒 + 结果解释 + 后续随访”的系统。它不是给患者下诊断，而是把研究数据整理清楚，帮助研究人员和医生发现哪些对象值得进一步查看，并说明系统为什么这样排序。

### 2.2 系统用大白话来说做什么

可以把系统想象成一个有记录能力的研究助手：

1. 先把一个人的不同来源资料收集到一起。
2. 检查资料有没有缺失、填错、重复或时间对不上。
3. 根据研究知识和这个人的资料，整理出一张“相关因素关系图”。
4. 根据这张图和预警模型，给出队列内的关注程度排序。
5. 解释排序主要参考了哪些资料，哪些资料还不够，哪些地方需要医生或研究人员复核。
6. 记录复核结果，安排后续随访，并生成研究报告。

系统回答的问题是：“按照目前收集到的研究资料，这名受试者在当前研究队列中是否需要更多关注，系统主要参考了什么？”

系统不回答的问题是：“这名患者已经确诊了吗？”“某个因素一定会导致发病吗？”“应该吃什么药？”

### 2.3 四段主线到底是什么意思

| 研究主线 | 大白话解释 | 系统里会看到什么 |
|---|---|---|
| 多源数据融合 | 把档案、访视、量表、APOE、MRI 等不同地方来的资料，按同一个人和同一时间整理到一起 | 数据来源、时间、缺失项、异常项和质量状态 |
| 个体化因果图谱构建 | 不是只给所有人看同一张图，而是结合某个受试者当前资料，挑出与他/她更相关的节点和关系 | 节点、箭头、当前激活路径、证据等级和缺失路径 |
| 因果引导的预警模型建立 | 让模型重点参考图谱中的关键因素和关系，得到一个研究队列内的关注程度排序 | 风险排序层、模型版本、数据版本和预警任务状态 |
| 个体化可解释性分析 | 用这个人的数据解释“为什么这样排序”，同时说明不能确定什么、还缺什么 | 主要贡献、相关路径、缺失指标、限制和人工复核意见 |

### 2.4 多源数据融合是什么

“多源”就是资料来自多个地方；“融合”不是简单地把几个文件拼接起来，而是要先确认这些资料是不是属于同一个人、发生在什么时候、单位是否一致、有没有重复或明显错误。

例如，某个受试者有一条 2026 年 1 月的认知量表记录、一条 2026 年 2 月的 MRI 记录和一条 APOE 记录。系统会把它们按受试者编号和采集时间整理起来，同时标出 MRI 是否缺失、认知量表是否超出合理范围、不同资料的版本是什么。这样，后面的图谱和模型使用的是一份有来源、有时间、有质量状态的资料，而不是一堆无法核对的数字。

### 2.5 个体化因果图谱是什么

可以先把“图谱”理解成一张关系图：圆点代表因素，箭头代表研究中关注的关系。例如“年龄”“认知量表变化”“脑部影像指标”“风险排序”可以成为不同节点，节点之间用箭头表示研究知识或模型关注的方向。

“个体化”表示每个人看到的重点不完全一样。系统会根据当前受试者已经有的数据，标出哪些节点有观测值、哪些关系在当前资料下被激活、哪些地方因为缺失资料不能判断。它表达的是“在当前研究资料和假设下，哪些关系值得关注”，不是证明某个因素一定造成了疾病。

### 2.6 系统功能模块拆解

| 模块 | 主要做什么 | 谁主要使用 | 开发同学可以理解为 |
|---|---|---|---|
| 登录和角色权限 | 判断是谁登录，以及能看哪些页面和数据 | 所有人 | 登录、菜单和权限拦截 |
| 受试者档案 | 管理脱敏编号、基本资料和历史访视 | 研究人员、医生 | 受试者 CRUD 和详情页 |
| 多源数据管理 | 录入或导入临床、认知、APOE、MRI 等资料 | 研究人员 | 表单、CSV 导入和字段映射 |
| 数据质量检查 | 找缺失、重复、异常和时间问题 | 研究人员、医生 | 校验规则、质量报告和阻断状态 |
| 个体化因果图谱 | 展示当前受试者的重要因素和关系路径 | 研究人员、医生 | 图谱 JSON、节点/边和图谱页面 |
| 研究型风险预警 | 根据图谱和模型给出队列内关注程度排序 | 研究人员、医生 | 创建任务、调用模型和保存结果 |
| 个体化解释 | 解释主要参考了什么、还缺什么、有什么限制 | 研究人员、医生 | 贡献列表、路径说明和限制文案 |
| 随访管理 | 记录下一次联系或检查的时间和事项 | 医生 | 随访计划、完成记录和提醒 |
| 报告与审计 | 导出研究报告，并记录谁在什么时候做了什么 | 管理员、研究人员、医生 | 报告导出、操作日志和问题追踪 |
| DeepAgent 子模块 | 按固定顺序串起四段研究工具 | 系统内部 | Python 工作流，不是独立用户或主系统 |

### 2.7 一次完整使用示例

研究人员选择 `DEMO-001`，导入该受试者的访视、认知量表和 MRI 资料。系统先检查资料，发现 MRI 缺失，于是标记为 `WARN`，并提示结果需要复核。接着系统生成当前受试者的条件性图谱，调用研究型预警模型，返回一个队列内的排序层。结果页同时展示主要参考因素、缺失的 MRI 信息和“预测解释，不是病因证明”的限制说明。医生确认后，可以创建下一次随访并导出报告。

### 2.8 范围外事项

- 不实现自动诊断、处方、用药推荐和治疗决策。
- 不把研究型风险排序描述成临床风险结论，不展示“已确诊”或“必然导致”等表述。
- 第一版不要求引入图数据库；个体化图谱以版本化 JSON 保存于评估结果，便于课程项目部署。
- 第一版不要求外部大模型服务；DeepAgent 可以由确定性流程和白名单工具实现。
- NACC 等外部数据未完成授权和独立验证前，不在页面显示伪造的外部验证指标。

### 2.9 典型用户旅程

| 步骤 | 操作 | 系统输出 | 失败时行为 |
|---|---|---|---|
| 1 | 用户登录并按角色进入工作台 | 菜单和数据范围按角色权限过滤 | 401 未登录或 403 无权限 |
| 2 | 研究人员导入或录入多源数据 | 导入任务、字段映射、错误行和数据版本 | 导入任务置为 FAILED，不写入错误记录 |
| 3 | 系统执行数据质量检查 | `PASS/WARN/BLOCKED` 和缺失/异常摘要 | `BLOCKED` 阻断后续评估 |
| 4 | 创建研究型评估任务 | 任务 ID、阶段和进度 | 参数错误返回 400，重复提交返回相同任务 |
| 5 | Java 调用 Python DeepAgent | 图谱、预警和解释结构化结果 | 超时/版本错误进入 FAILED |
| 6 | 医生或研究人员复核 | 复核意见和审核时间 | 未复核结果标注 `PENDING` |
| 7 | 创建随访并生成报告 | 随访计划、报告和审计日志 | 报告必须保留版本和限制说明 |

## 3. 角色、权限与系统边界

### 3.1 角色定义

| 角色 | 主要任务 | 可以查看 | 不可以做 |
|---|---|---|---|
| 管理员 `ADMIN` | 用户、角色、模型版本、系统状态和审计 | 全局配置和运行状态 | 不直接修改历史评估结果 |
| 研究人员 `RESEARCHER` | 导入数据、创建评估、查看图谱/模型/研究报告 | 授权研究队列的完整研究字段 | 不越权查看未授权数据 |
| 医生 `DOCTOR` | 查看结果、复核、创建随访和查看解释 | 被授权受试者的业务结果和复核信息 | 不发布或修改模型算法 |
| 患者端 `PATIENT` | 查看通俗摘要、随访时间和沟通事项 | 自己的脱敏摘要和随访安排 | 不查看风险分数、模型系数、图谱权重或 Agent 内部信息 |
| Agent 客户端 `AGENT_CLIENT` | Java 与 Python 服务之间的内部调用 | 当前任务所需的脱敏结构化数据 | 不作为用户登录，不访问 Java 数据库 |

### 3.3 边界原则

```text
浏览器 → Java Controller → Java Service → Repository / AgentClient
                                      ↘ 业务状态、质量校验、审计、持久化
AgentClient → Python DeepAgent（只接收脱敏结构化数据）
```

- 浏览器不得直接访问 Python 服务。
- Controller 不得直接调用 Repository 或 AgentClient，必须由 Service 编排。
- Python Agent 不得直接访问 Java 数据库，也不得修改 Java 的任务状态。
- 所有进入页面的风险结果必须经过 Java 的版本、状态和质量校验。

## 4. 总体架构与分层规范

### 4.1 组件职责

| 组件 | 技术建议 | 职责 | 明确不负责 |
|---|---|---|---|
| Web 前端 | Vue 3 + Element Plus 或现有 HTML/CSS/JS | 路由、角色视图、表单、状态展示和交互校验 | 直接访问数据库或 Python 服务 |
| Controller 层 | Spring MVC | 接收请求、认证授权、参数校验、统一响应 | 编写模型逻辑和复杂事务 |
| Service 层 | Spring Service | 编排业务、质量闸门、任务状态、事务和审计 | 依赖具体 HTTP 实现细节 |
| Repository/Data 层 | MyBatis-Plus 或 JPA + MySQL | 数据查询、持久化、分页和索引 | 处理页面展示逻辑 |
| AgentClient | Java HTTP Client | 调用 Python、超时、重试、契约校验和结果映射 | 绕过 Service 写数据库 |
| Python DeepAgent | FastAPI/Flask + 研究工具 | 固定顺序编排四类研究工具、生成结构化结果 | 用户权限、Java 数据库和人工复核 |

### 4.2 Java 包结构

```text
backend/src/main/java/com/example/adcausalrisk/
├─ controller/       # 外部 HTTP 接口和权限注解
├─ service/          # 应用业务、事务、质量闸门、任务编排
├─ domain/           # 领域对象、枚举、状态转换规则
├─ entity/           # 持久化实体
├─ repository/       # Mapper/Repository
├─ dto/              # Request/Response/分页对象
├─ agent/            # DeepAgentClient、契约 DTO、响应校验
├─ algorithm/        # 迁移期 PythonRiskScoringAdapter
├─ validator/        # 参数、版本、数据质量和安全校验
├─ security/         # 登录、会话、RBAC、脱敏
├─ exception/        # 业务异常、错误码、统一异常处理
└─ config/           # 数据源、HTTP 客户端、跨域和文档配置
```

### 4.3 分层调用规则

| 规则 | 要求 | 示例 |
|---|---|---|
| R-ARCH-01 | Controller 只处理 HTTP 语义，不写业务判断 | `AssessmentController` 调用 `AssessmentService` |
| R-ARCH-02 | Service 统一控制事务和状态变更 | 创建任务、写审计、调用 Agent 必须有任务状态 |
| R-ARCH-03 | Repository 不接收页面 DTO | 使用 Entity 或 Query 对象访问数据库 |
| R-ARCH-04 | AgentClient 只由 Service 调用 | 不允许前端或 Controller 直接拼 Python URL |
| R-ARCH-05 | 外部接口只暴露 DTO | 不把数据库 Entity 直接序列化返回前端 |

## 5. 功能需求

### 5.1 认证、用户与权限

| 编号 | 优先级 | 需求 | 验收条件 |
|---|---|---|---|
| FR-AUTH-01 | P0 | 支持用户名和密码登录、退出和当前用户查询 | 未登录访问业务接口返回 401；退出后会话失效 |
| FR-AUTH-02 | P0 | 按 `ADMIN/RESEARCHER/DOCTOR/PATIENT` 返回菜单和数据范围 | 不同角色登录后看到的菜单和操作按钮不同 |
| FR-AUTH-03 | P0 | 密码不可明文保存，登录失败不暴露账号是否存在 | 数据库无明文密码；错误提示统一 |
| FR-AUTH-04 | P1 | 记录登录、退出、失败登录和权限拒绝审计 | 管理员可按用户、时间和事件查询 |

### 5.2 受试者与多源数据

| 编号 | 优先级 | 需求 | 验收条件 |
|---|---|---|---|
| FR-DATA-01 | P0 | 支持受试者档案的新增、查询、修改和详情查看 | 支持编号、别名、状态和创建时间查询 |
| FR-DATA-02 | P0 | 支持访视、临床、认知、APOE 和 MRI 指标录入 | 字段、单位、采集时间和缺失原因可保存 |
| FR-DATA-03 | P0 | 支持 CSV 导入预览、字段映射和错误行下载 | 未通过校验的行不能直接入库 |
| FR-DATA-04 | P0 | 为每次导入生成 `dataVersion` 和导入任务 | 同一文件重复提交可识别，不产生重复数据 |
| FR-DATA-05 | P0 | 对多源数据做身份脱敏、时间对齐、重复和异常检查 | 生成质量明细和汇总，不覆盖原始导入记录 |

### 5.3 数据融合与质量闸门

| 编号 | 优先级 | 需求 | 验收条件 |
|---|---|---|---|
| FR-QUALITY-01 | P0 | 汇总临床、认知、APOE、MRI 的覆盖率和时间范围 | 页面能看到各来源有效、缺失和异常数量 |
| FR-QUALITY-02 | P0 | 质量状态只允许 `PASS/WARN/BLOCKED` | `BLOCKED` 时评估按钮禁用或创建后立即阻断 |
| FR-QUALITY-03 | P0 | 保存质量规则版本、检查时间和执行人 | 结果可追溯到规则版本和数据版本 |
| FR-QUALITY-04 | P1 | 对 WARN 给出可读的复核提示和缺失项 | 医生可以看到哪些数据需要补充或复核 |

### 5.4 个体化图谱、预警和解释

| 编号 | 优先级 | 需求 | 验收条件 |
|---|---|---|---|
| FR-ASSESS-01 | P0 | 选择受试者、模型版本和预测窗口创建评估任务 | 返回唯一 `taskId`，重复请求可幂等查询 |

| FR-GRAPH-01 | P0 | 保存并展示当前受试者的条件性节点、路径、方向和证据等级 | 图谱页面能区分激活路径、普通路径和缺失路径 |
| FR-WARN-01 | P0 | 基于图谱变量和关系生成研究型风险排序 | 结果同时显示模型版本、数据版本和质量状态 |

| FR-EXPLAIN-01 | P0 | 展示预测贡献、条件性路径、缺失指标、证据等级和限制 | 页面明确“预测解释，不是病因证明” |

## 6. 业务流程与状态机

### 6.1 评估任务主流程

```text
POST /api/assessment-tasks
        ↓
创建 PENDING 任务并检查权限、受试者、模型和数据版本
        ↓
DATA_FUSION：融合数据并执行质量闸门
        ├─ BLOCKED → 任务 BLOCKED，riskScore=null，结束
        └─ PASS/WARN → 进入下一阶段
        ↓
CAUSAL_GRAPH：构建个体化条件因果图谱
        ↓
WARNING_MODEL：调用因果引导预警工具
        ↓
EXPLANATION：生成个体化贡献、路径、缺失项和限制
        ↓
Java 校验并持久化结果，任务 COMPLETED
        ↓
REVIEW：医生/研究人员人工复核，随后创建随访或报告
```

### 6.2 任务状态转换

| 当前状态 | 允许的下一状态 | 触发条件 |
|---|---|---|
| `PENDING` | `RUNNING`、`FAILED` | 参数、权限和数据版本检查完成 |
| `RUNNING` | `COMPLETED`、`BLOCKED`、`FAILED` | Agent 完成、质量阻断或调用异常 |
| `COMPLETED` | `REVIEWED` | 医生或研究人员提交复核 |
| `BLOCKED` | `PENDING` | 补齐数据后由授权用户重新创建新任务，不覆盖原任务 |
| `FAILED` | `PENDING` | 修复服务或契约后重试，保留原失败记录 |
| 任意终态 | — | 不允许通过普通接口直接修改历史结果 |

### 6.3 四段研究阶段的输入输出

| 阶段 | 输入 | 输出 | Java 侧处理 |
|---|---|---|---|
| `DATA_FUSION` | 多源受试者数据、数据版本、规则版本 | 对齐后的特征、质量状态、缺失项 | 校验质量；BLOCKED 时停止 |
| `CAUSAL_GRAPH` | 统一特征、研究先验、个体观测 | 节点、边、路径、证据等级 | 保存图谱 JSON 和版本 |
| `WARNING_MODEL` | 图谱关键变量和模型版本 | riskScore、riskLevel、模型说明 | 校验版本和分数范围 |
| `EXPLANATION` | 预警结果、图谱路径、缺失项 | 贡献、条件性路径、限制说明 | 按角色过滤后展示 |

### 7.5 Python DeepAgent 内部接口（目标契约）

| 方法 | 路径 | 调用方 | 说明 |
|---|---|---|---|
| GET | `/api/health` | Java AgentClient | 检查服务、契约和工作流版本 |
| POST | `/api/agent/v1/runs` | Java AgentClient | 提交一次四段研究流程 |
| GET | `/api/agent/v1/runs/{runId}` | Java AgentClient | 查询阶段、状态和结构化结果 |

请求最小字段：

```json
{
  "contractVersion": "deepagent-v1",
  "runId": "run-20260920-0001",
  "subjectCode": "DEMO-001",
  "dataVersion": "demo-2026-09",
  "modelVersion": "deepagent-causal-warning-v1",
  "predictionWindowMonths": 24,
  "visits": [],
  "features": []
}
```

响应最小字段：

```json
{
  "status": "COMPLETED",
  "contractVersion": "deepagent-v1",
  "runId": "run-20260920-0001",
  "workflowVersion": "causalrisk-workflow-v1",
  "currentStage": "EXPLANATION",
  "dataVersion": "demo-2026-09",
  "modelVersion": "deepagent-causal-warning-v1",
  "qualityStatus": "WARN",
  "riskScore": 0.62,
  "riskLevel": "MEDIUM",
  "warnings": ["MRI 数据缺失，结果需人工复核"],
  "graph": {"nodes": [], "edges": [], "paths": []},
  "explanations": [],
  "limitations": ["研究型排序，不是临床诊断"]
}
```

Java 必须执行以下校验：

- `contractVersion`、`workflowVersion`、`dataVersion` 和 `modelVersion` 是否与任务一致。
- `qualityStatus=BLOCKED` 时强制清空 `riskScore`，并把任务置为 `BLOCKED`。
- `riskScore` 必须为空或位于 `[0,1]`；`riskLevel` 不合法时任务置为 FAILED。
- 响应缺字段、超时、HTTP 5xx、连接失败或 `runId` 不一致时任务置为 FAILED。
- 当前 Python 服务已有 `stage4-v1` 的兼容评分接口时，只能作为迁移适配器使用，不能绕过 Java 任务和质量校验。

### 7.6 统一错误码

| 错误码 | HTTP | 含义 | 前端处理 |
|---|---:|---|---|
| `AUTH_401` | 401 | 未登录或会话过期 | 跳转登录页 |
| `AUTH_403` | 403 | 角色无权操作 | 显示无权限提示，不重试 |
| `SUBJECT_404` | 404 | 受试者不存在或不可见 | 返回列表并提示 |
| `VALIDATION_400` | 400 | 参数或字段校验失败 | 高亮表单字段 |
| `QUALITY_BLOCKED` | 409 | 数据质量阻断 | 展示缺失项和修复建议 |
| `AGENT_TIMEOUT` | 504 | Python 调用超时 | 显示服务暂不可用，可由授权用户重试 |
| `AGENT_CONTRACT_MISMATCH` | 502 | 契约或版本不匹配 | 阻止结果展示并记录审计 |
| `ASSESSMENT_FAILED` | 500 | 评估流程失败 | 展示 `traceId`，不显示伪造分数 |

## 8. 数据模型与持久化

### 8.1 核心实体关系

```text
sys_user 1 ─── n audit_log
subject 1 ─── n subject_visit
subject 1 ─── n subject_feature
subject 1 ─── n data_import_job
subject 1 ─── n assessment_task 1 ─── 1 risk_assessment
assessment_task 1 ─── n agent_run
risk_assessment 1 ─── n risk_explanation
risk_assessment 1 ─── n follow_up_plan
```

### 8.2 关键表字段

| 表 | 必备字段 | 约束 |
|---|---|---|
| `sys_user` | `id`, `username`, `password_hash`, `role`, `status`, `created_at` | `username` 唯一；密码不可明文 |
| `subject` | `id`, `subject_code`, `alias`, `sex`, `birth_year`, `status`, `data_version` | `subject_code` 唯一；第一版只允许脱敏编号 |
| `subject_visit` | `id`, `subject_id`, `visit_date`, `visit_no`, `mmse`, `moca`, `cdr`, `missing_reason` | `subject_id + visit_no` 唯一 |
| `subject_feature` | `id`, `subject_id`, `source_type`, `feature_name`, `feature_value`, `unit`, `observed_at`, `quality_status` | 按 `subject_id + source_type + observed_at` 建索引 |
| `data_import_job` | `id`, `file_name`, `data_version`, `status`, `total_rows`, `valid_rows`, `error_rows`, `created_by` | 保存原始文件摘要和错误报告，不覆盖历史版本 |
| `assessment_task` | `id`, `subject_id`, `status`, `current_stage`, `agent_run_id`, `workflow_version`, `model_version`, `data_version`, `trace_id` | `idempotency_key` 唯一；记录失败原因 |
| `risk_assessment` | `id`, `task_id`, `risk_score`, `risk_level`, `quality_status`, `graph_json`, `result_json`, `review_status` | BLOCKED 不保存可用分数 |
| `risk_explanation` | `id`, `assessment_id`, `contribution_json`, `path_json`, `limitations_json` | 不保存原始提示词或内部推理文本 |
| `follow_up_plan` | `id`, `subject_id`, `assessment_id`, `planned_at`, `status`, `owner_id`, `notes` | 关联来源评估，可追溯 |
| `audit_log` | `id`, `actor_id`, `event_type`, `resource_type`, `resource_id`, `trace_id`, `summary`, `created_at` | 禁止写入密码、原始身份和敏感内部提示词 |

### 8.3 数据质量规则

| 规则编号 | 检查内容 | WARN | BLOCKED |
|---|---|---|---|
| Q-01 | 关键字段缺失 | 非关键指标缺失 | 受试者编号、访视日期或核心输入缺失 |
| Q-02 | 数值范围 | 少量异常待复核 | 核心特征全部无效 |
| Q-03 | 时间一致性 | 访视间隔异常 | 存在无法排序或明显未来日期 |
| Q-04 | 数据版本 | 数据源混合但可追溯 | 版本缺失或与模型不兼容 |
| Q-05 | 身份安全 | 发现待清理的展示字段 | 含真实身份标识，禁止发送 Agent |

## 9. 前端信息架构与页面规范

### 9.1 导航结构

| 角色 | 一级导航 | 页面目标 |

### 9.2 页面清单

| 页面 | 必须展示 | 必须处理的状态 |
|---|---|---|
| 登录页 | 账号、密码、系统用途提示 | 登录失败、锁定、网络异常 |

| 结果页 | 风险排序、图谱路径、解释、限制和复核入口 | BLOCKED 时不显示分数 |
| 随访页 | 计划时间、负责人、事项、完成记录 | 逾期、取消、无计划 |
| 报告页 | 研究结果、版本、生成时间、非临床声明 | 导出失败、报告过期 |

### 9.3 可读性基线

- 正文建议不小于 14px，页面主标题不小于 24px，按钮文字不小于 14px。
- 研究术语旁必须提供简短解释；患者端使用“需要进一步关注”等通俗文案。
- 状态不能只用颜色表达：同时显示文字和图标；`PASS` 使用绿色，`WARN` 使用橙色，`BLOCKED/FAILED` 使用红色或深灰色。
- 页面必须有加载、空数据、失败和无权限四种状态；禁止出现空白区域或残缺卡片。
- 每个结果页明确显示“研究型结果，仅供研究与随访参考，不构成诊断”。

## 10. 非功能需求

### 10.1 性能与稳定性

| 编号 | 要求 | 验收方式 |
|---|---|---|
| NFR-PERF-01 | 本地演示环境首页和列表接口 95% 请求小于 2 秒 | 使用固定 100 条合成数据压测 30 次 |
| NFR-PERF-02 | 列表接口必须分页，单次最多返回 100 条 | 检查接口参数和数据库查询日志 |
| NFR-PERF-03 | Agent 连接超时、读取超时和重试次数可配置 | 使用 Mock 服务模拟超时和 5xx |
| NFR-REL-01 | Python 服务不可用时 JavaWeb 仍可登录、查看历史数据和审计 | 停止 Python 服务执行冒烟测试 |
| NFR-REL-02 | 任务状态和 Agent 调用日志可恢复查询 | 重启 Java 后查询任务状态 |

### 10.2 安全、隐私与审计

- 所有业务接口执行认证和角色授权；对象级查询还要检查数据范围。
- Agent 只接收 `DEMO-*` 或已脱敏的 `subjectCode`，禁止传输姓名、身份证、电话、住址等身份信息。
- 日志只记录摘要、版本、`traceId` 和错误码，不记录密码、原始数据和内部提示词。
- 导出报告包含数据版本、模型版本、工作流版本、生成时间和研究用途声明。
- 所有质量阻断、人工复核和结果导出都必须写入审计日志。

### 10.3 可维护性

- 所有枚举、错误码和外部路径集中定义，不在 Controller 中散落字符串。
- DTO、数据库字段和 Python 契约变更必须先更新本文档、JSON 样例和接口测试。
- Java 侧保留 `AgentClient` 接口，`stage4-v1` 迁移适配器和 `deepagent-v1` 实现不能影响业务层。
- 研究结果必须带模型和数据版本，禁止覆盖历史结果。

## 14. 风险、限制与最终定位

### 14.1 当前实现与目标契约

| 项目 | 当前基础 | 本文目标 |
|---|---|---|
| Python 健康检查 | `/api/health` | 保留，并返回服务/契约/工作流版本 |
| Python 评分兼容接口 | `stage4-v1`、`/api/research/predict` | 由 Java `algorithm/` 适配，作为迁移期兼容实现 |
| DeepAgent 工作流 | 现有研究工作流/确定性编排 | 统一到 `deepagent-v1` runs 契约 |
| 图谱存储 | 评估结果 JSON | 第一版继续使用版本化 JSON，不新增图数据库 |
| 外部大模型 | 非必需 | 不作为第一版启动条件 |

### 14.2 必须向用户和答辩评委说明

- 本系统是研究和教学演示用的风险预警与可解释随访管理平台，不是医疗诊断系统。
- 风险分数是研究型排序结果；因果图谱路径是条件性研究解释，不是个体病因证明。
- Agent 只是固定研究流程的编排子模块，JavaWeb 才是系统主体；所有结果都要经过 Java 质量校验和人工复核。
- 数据缺失、模型版本不匹配、服务异常和外部验证未授权时，系统必须诚实显示限制或阻断状态。

### 14.3 最终产品定位

一个以“多源数据融合 → 个体化因果图谱构建 → 因果引导的预警模型建立 → 个体化可解释性分析”为核心研究链路、以 Spring Boot JavaWeb 承载应用业务、以 Python DeepAgent 作为受限流程编排子模块的阿尔茨海默病风险预警与可解释随访管理系统。
